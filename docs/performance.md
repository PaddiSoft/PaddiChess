# 搜索与界面性能

[文档目录](README.md) · [引擎说明](engines-and-models.md)

## 先区分耗时来源

外部一手棋经历捕获、识别、落点确认、搜索／模型请求、发送与目标响应。引擎 NPS 只描述搜索吞吐量，不能直接代表界面流畅度或端到端落子延迟。

33 ms、80 ms、250 ms 是观察目标间隔。识别耗时、棋子动画、系统调度和目标是否产生新帧都会改变实际节奏；减少间隔不能跳过稳定落点核验。

## 搜索参数

| 参数 | 含义与选择方法 |
| --- | --- |
| 棋力 0–20 | 20 为完整执棋搜索；较低等级通过引擎能力或受限选招调整，不保证不同插件同级同强 |
| CPU 线程 | 增加搜索并行度，也与截图、录屏和 UI 竞争；比较同一局面下的速度与响应，而非只取最大值 |
| 置换表 Hash | 保存已搜索信息；当前界面上限 16384 MB，更大不必然更快，修改时需要重新分配 |
| 思考时间 | 每步搜索预算，不包含首次进程准备、截图、API 网络和目标输入时间 |
| 深度限制 | 默认关闭；明确开启后，时间或深度任一先到都会停止 |
| MultiPV | 同时分析多个候选，会分散资源；20 级执棋侧重最佳方案，复盘时可增加候选比较 |
| 分阶段时间 | 可选，默认关闭；用于 20 级执棋预算，手动分析仍使用相应统一设置 |
| 外部评分 | 自动模式复用我方执棋评分；持续双方评分会占用额外资源 |

给系统和其他程序保留内存。Hash 太大导致换页时可能更慢；同时运行多个引擎或本地模型时，分别计算它们的内存需求。长分析设置不适合直接照搬到短时实战。

随包引擎的高名义深度不表示穷举了全部分支；将杀剪枝等机制也会影响层数。按时间比较相同局面更容易得到可重复结果。

## 分阶段预算

开局、中局、残局预算用于分配时间，不等于识别局面难度。标准开局或首回合合法局面接入可以保留开局判断；其他中途局面不会因为“本地刚开始记录”就被当作开局。

残局分组使用子力阈值，车计 2，马／炮计 1。少子局也可能很复杂，是否给更长时间取决于实际对局时钟。

## 测速方法

1. 固定引擎、NNUE、局面、Hash 和搜索时长。
2. 用“按当前线程／置换表测速”比较几档线程数。
3. 分别观察引擎吞吐与同时截图／录屏时的界面响应。
4. 记录是否冷启动、是否预热、运行次数和系统负载。

不要把不同网络、不同搜索参数或不同机器的单次 NPS 直接当棋力排名。API 延迟还受服务排队、模型推理和网络影响，增加本机线程不会加速远程模型。

## 当前实现采取的优化

- macOS 支持时复用常驻捕获会话，Windows 复用捕获缓冲；完全相同的有效观测可复用特征。
- 正常追踪不逐帧跑全盘 OCR；初始化、必要恢复和落子前核验使用象棋专用模型，中文 OCR 仅补查不确定格子。
- 观察与搜索／模型请求、输入任务分别调度，取消的旧结果通过局面和配置身份检查被丢弃。
- 接管棋子动画比普通对弈短；动画设为 0 可关闭棋盘和界面动效。
- 指标文字限制刷新频率，棋谱／模型目录使用虚拟化。
- 设置合并后后台原子写；历史候选事件只追加小日志，关键节点才保存完整棋谱。

这些优化都必须保留新帧有效性、棋子身份和最终落点核验。把中间动画当作落点会产生更快但错误的输入。

## v1.0.3 识别性能

默认全盘识别已由多视图中文 OCR 改为象棋专用模型。离线比较中，专用模型预热后整盘中位约 182 ms，mobile 中文 OCR 原流程约 8.84 秒；客户端另加置信度核验，少量不确定位置有 800 ms 的 OCR 补查预算。模型比较、样本数量及限制详见[离线象棋识别](recognition.md)。这些耗时不包含截图、定位、搜索或输入，也不表示逐帧全盘推理。

## 先前定位与 OCR 测量

2026-10-06 在 Apple M3、.NET 10 Release 构建上，使用固定截图比较自动定位前后的同一候选搜索：中局、开局、完整窗口和网页棋盘四组热调用中位数由约 697–1312 ms 降至 437–466 ms，四角坐标没有变化。每组热调用 5 次；没有独占机器，因此这些数值用于说明重复扫描优化的效果，不是对所有机器的延迟承诺。

同次离线字符识别采用 2 个推理线程。两张完整测试棋盘首次／预热后识别约 4–5 秒，其中模型首次加载约 150 ms，主要耗时在不确定字符的多视图推理。这是切换专用模型前的完整 OCR 路径测量；正常接管使用增量观测、已确认的棋子样本和精确缓存，不逐帧重复这项工作。识别日志中的逐帧毫秒数也不能代表首次完整 OCR 耗时。

整盘回归检查 90 个位置、阵营、方向和 FEN，包含原始图、颜色通道变换、反色及曝光变化，并绕过内置皮肤模板。低分辨率用例另行验证：读不清的棋子必须保留不确定状态，不允许作为空格或错误棋子直接放行。有限样本通过不代表任意皮肤达到某个准确率。

## GPU 与 NativeAOT

棋盘专用识别模型和中文 OCR 已支持自动加速：Windows DirectML、macOS CoreML，以及 Windows 上兼容的已安装 NPU 提供程序。设备失败回退 CPU，后台预热时已有 CPU 会话继续识别。具体条件、混合推理含义及 CPU / GPU 对照数据见[识别加速说明](recognition.md#gpu--npu-与-cpu-回退v104)。GPU 不保证每种小批次都更快。

随包 Pikafish 的搜索与 NNUE 推理使用 **CPU**，没有把 RTX 显卡用于该引擎执棋的开关。界面绘制、录屏或独立部署的本地模型可以有不同的 GPU 使用方式，不能与 Pikafish 搜索混为一谈。

当前发布未开启 **NativeAOT**。Avalonia UI、托管启动和独立原生引擎属于不同性能范围；AOT 不会提高 Pikafish 算法本身的搜索能力。未来评估 AOT，需要分别验证包体、启动、内存、反射、JSON、ONNX 及跨平台发布兼容性。

完整测试、微基准、原生窗口实验与真实第三方对局分别说明不同问题；发布说明应标明测量范围，不能用一种结果替代另一种验证。
